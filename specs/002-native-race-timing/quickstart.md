# Phase 1 — Validation quickstart

These are acceptance runs for the planned Android app and the existing JAuswertung plugin.

## Setup

### Live desktop prerequisite (T008)

1. Use a Java 25 build of JAuswertung from the timing feature source with its plugin descriptor and matching Core changes. The official 18.1.1 installer lacks those changes. Follow the [Spec 001 build instructions](../001-phone-race-timing/quickstart.md) and record the exact source revision, any unpublished patch needed to reproduce it, the build and launch commands, and the artifact or classpath used.
2. Launch the real JAuswertung application. Open **Information → Zeitnahme**, enable trusted local HTTPS and verify a one-time code pairs a test client. Record the smoke-test result. If the smoke test used the role needed for the Android run, restart the disposable listener session to free that role, then issue a fresh code.
3. Complete T008 before live Android pairing, emulator integration or physical timing tests. If the matching desktop cannot run because of `filechooser-platform` or another dependency, record the blocker and leave the live checks pending. Android unit and fixture-based contract tests can run independently.

### Android test setup

1. Prepare JDK 17, the Android SDK for API 37, Android SDK Platform Tools and an emulator or a physical Android 10+ pilot device. Use the project's Gradle Wrapper once the Android module exists.
2. For live runs, use a disposable competition heat with at least three populated lanes and choose the **Wettkampftisch** starter. Use a trusted certificate with a SAN matching the address entered on Android. For an emulator loopback run, bind the desk to `127.0.0.1` and use `https://10.0.2.2:<port>` with a corresponding SAN and the pilot CA. For a physical run, use the selected desk LAN address reachable from the venue WLAN.
3. In the planned `android-race-timing/` directory, run the Windows commands below once the tasks are implemented.

```powershell
.\gradlew.bat :app:testDebugUnitTest :app:assembleDebug
.\gradlew.bat :app:connectedDebugAndroidTest
.\gradlew.bat :app:installDebug
```

### Android pairing check (T009–T011, 2026-11-23)

The Android 17 emulator paired over HTTPS against the verified Windows pilot. Before arming it showed standby. After arming it showed lane 3 for phone timing and lane 4 for manual entry, with lane 5 assigned to the other device and absent from the Android screen. After an app process restart, the original pairing restored the lane view. The app returned to the pairing screen with an expiry message after the desk invalidated the credential.

The emulator used `10.0.2.2` and a disposable pilot CA provisioned only for that host in a local debug build. The untrusted connection was rejected in a separate negative check. Instrumentation invoked the app's pairing action and verified the rendered screen. The regular Android source passed the five JVM tests, the debug APK build and Android Lint.

### Desk countdown and Android finish check (T012–T016, 2026-11-23)

The verified Windows pilot armed a synthetic heat and reached Ready after Android clock sampling over trusted loopback HTTPS. The emulator showed two assigned timed lanes (3 and 4). Both finish controls were disabled before the start and tapping them during the three short tones produced no capture. After the long tone, lane 3 could be captured and then became disabled while lane 4 stayed available. A repeated tap on lane 3 produced no extra result. The desk confirmed one timed finish per lane, 4,874,702 µs for lane 3 and 9,981,497 µs for lane 4, both classified as certain by the plugin. These are elapsed times for emulator taps. The independent timing reference and audible onset measurement are part of T025.

The seven JVM tests, the debug APK build and Android Lint passed. The clock contract tests covered five-second probe expiry, estimate scope mismatches and the inclusive 10,000 µs bound. Local emulator evidence is in `target/desktop-t008/android-finish-results.csv`.

### Android manual stopwatch check (T017–T019, 2026-11-23)

The verified Windows pilot assigned stopwatch lanes 3 and 4 to one Android 17 emulator. Both controls were disabled before the desk countdown. In the running heat, the app rejected `0` inline and the desk still had no results. Entering `1:05,20` in the lane 4 field produced one acknowledged result on lane 4 with exactly 65,200,000 µs and source `STOPPUHR_HANDY`. Lane 3 stayed available and had no result. This attempt used no clock estimate for the Android device.

All nine JVM tests, the debug APK build and Android Lint passed. Local desk evidence is in `target/desktop-t008/android-stopwatch-results.csv`.

### Android outbox recovery check (T020–T022, 2026-11-23)

The Android 17 emulator sent a timed finish for lane 3 to the verified Windows pilot over trusted HTTPS. The desk returned HTTP 200 before the Android test transport dropped the acknowledgement. The host copied the first request and acceptance evidence while the app still showed the event as pending, then stopped the app process without clearing its data.

In the second process, the app restored the pending event and resent the identical payload, including the original event ID, process epoch and estimate. Lane 4 stayed disabled until a new qualifying clock estimate arrived. The pilot applied exactly one result per lane. After Apply, the original lane 3 submission still received HTTP 200 and a new submission for the closed attempt received HTTP 409 (`geschlossen`).

The three local Android instrumentation checks passed for transaction rollback, durable replay and 401 blocking. Both live restart phases, all nine JVM tests, debug app and test APK builds, and Android Lint passed. Local evidence is in `target/desktop-t008/android-outbox-evidence/`. The complete mixed-mode run with an actual connectivity interruption is part of T024.

### Android installation, network and backup checks (T023)

- **Installation and tests** — The debug APK installed and opened on the Android 10 (API 29) and Android 17 (API 37) emulators. The APK declares minimum API 29 and target API 37. All nine JVM tests, the debug app and test APK builds, Android Lint, and the three self-contained outbox instrumentation checks passed. The two live restart phases were verified separately under T020.
- **HTTPS and certificates** — Android 10 and 17 rejected an HTTP origin and an untrusted certificate. Android 17 also rejected a certificate signed by the trusted test CA with the wrong IP SAN. The fixture received no pairing request for the rejected cases. A certificate from the same test CA with the correct SAN allowed pairing and reading the desk state. The disposable CA was installed in the Android 17 emulator and accepted by the existing debug trust rule for `10.0.2.2`.
- **Local network permission** — Android 10 offered pairing without a separate permission prompt. Android 17 kept pairing blocked and showed the explanation after the system dialog was denied. Granting the permission through the next prompt allowed the HTTPS pairing.
- **Backup exclusions** — The framework backed up and restored a control file through Android's LocalTransport on both versions. The pairing preference and the Room database, WAL and SHM files were absent after reinstall and restore. On Android 17 the test passed in both cloud-backup mode and simulated device-transfer mode with `is_device_transfer=true`.

The Android 17 image needed a restart of System UI after its first boot. The test runs above completed on that emulator. Local evidence is in `target/t023/`.

### Integrated Android heat with a network outage (T024, 2026-11-23)

The verified Windows pilot opened a disposable competition in JAuswertung and started HTTPS from **Information → Zeitnahme**. An Android 10 emulator paired with the debug APK using a disposable pilot CA. Android instrumentation invoked the app's capture actions with the regular HTTPS client and Room outbox. The clock readiness limit stayed at 10 ms. The countdown was active before the attempt had a start timestamp, and the app blocked capture until it observed the running heat.

The desk accepted a timed finish on lane 3 while connected. During a simulated interruption of the connection to the desk, Android stored a timed finish on lane 5 and a stopwatch time of `1:05,20` on lane 4. Both records were pending and the desk still had only lane 3. After reconnecting, Android automatically delivered the original event IDs, timestamps and clock estimates. The JAuswertung review had exactly one result for each of lanes 3, 4 and 5.

**Zeiten übernehmen** wrote 54, 6,520 and 102 centiseconds to lanes 3, 4 and 5 respectively in the live competition. The corresponding values were zero before Apply. Lane 6 held its preexisting 7,890 centiseconds before and after. The instrumentation passed. Local evidence is in `target/integrated-timing-validation/mixed-38sue9kl/`. The T020 lost-acknowledgement and process restart run above used the same desktop pilot.

The standard Java 25 `mvn -o verify` run still stopped at the unresolved `filechooser-platform` snapshot. The live test used the previously verified Windows build with the local FileChooser workaround.

## Complete heat and delivery recovery

1. Assign two timestamp lanes and one stopwatch lane to the same Android device. Pair with a single-use code and verify only those lanes appear with the correct modes. On target API 37, also deny and then grant local network access. Confirm that the UI explains the denial and recovers when granted.
2. Arm the heat, wait for the desk's Ready state and trigger the configured countdown from Swing. Verify that target capture stays disabled during the three short tones. After the long tone, record the first lane and confirm its button locks while the second stays available.
3. With the app already showing a running heat and its estimate still valid, interrupt access to the desk. Capture the second lane and see Pending. Restore access and verify one acknowledgement for the original event. For the sort of outage that prevents a new valid timed capture, verify it stays blocked and a stopwatch lane can still accept a positive elapsed time.
4. Enter a time such as `1:05,20` for the stopwatch lane. Reject zero, negative or malformed values. In Swing, review and apply all three intended times and verify their lanes and sources.
5. In a fresh attempt with two assigned timestamp lanes, run the T020 host-controlled restart check using `android-race-timing/tools/outbox-restart.ps1`. In the first instrumentation invocation, send a finish over HTTPS and record the desk's HTTP 200 with `angenommen: true` before the test transport seam withholds the acknowledgement. Export that evidence, the original event ID and payload to the test host before ending the invocation. Exclude pairing credentials. With the desk session and app data intact, stop the app process from the host and start a second invocation with replay held. Verify the restored Pending record, then allow replay and compare the original and retry ID and payload, including the old epoch and estimate. Verify Accepted and exactly one result for that lane at the desk. Hold fresh clock samples until the new process has observed the running heat. Confirm that the second lane stays disabled before a qualifying estimate arrives, then verify that the lane can capture using the new process epoch and estimate.
6. In a separate protocol check, confirm that an exact retry after Apply succeeds and a first-time submission for a closed attempt is rejected with a visible reason. Verify that an expired pairing blocks its queue and subsequent pairing leaves the old event in its original session.
7. Run negative pairing tests for HTTP, an untrusted chain and a wrong hostname.

For the host-controlled restart check, build and install the matched debug app and `:app:assembleDebugAndroidTest` APK on a disposable emulator with a trusted pilot CA. Run `tools/outbox-restart.ps1` with its ADB path, emulator serial, desk HTTPS origin, fresh pairing code and output directory. Pass `-StartHeat` and `-ApplyHeat` script blocks that start the armed desk heat and apply its two results. Each block must return after its desk action completes. Keep the same desktop session open through both instrumentation phases.

## Physical qualification

The [T025 pilot worksheet](pilot/t025.md) registers the 30 desk starts and provides the scoring command. Complete the independent reference setup and certificate check before the first scored run.

Qualify only the **Android client with the desk as starter** in T025. Use the applicable [Spec 001 SC-007 criteria](../001-phone-race-timing/spec.md#success-criteria), with app reopen in place of browser reload. Declare the readiness and audible-start limits up front, register at least 30 Android desk-start trials, and register a separate fault-recovery suite. Measure readiness from arming and count timeouts in the denominator. Check the 95% readiness target and the 10 ms clock-error limit for each timed lane in Ready trials, including reference uncertainty. Verify one configured race horn per successful start and measure audible onset and manual reaction separately. Use the proposed five-second window for comparison.

Keep the readiness and fault results separate and reconcile every capture. Report the device, Android version, WLAN and audio setup. Include a local WLAN without internet uplink while mobile data remains enabled. Record the results as partial evidence for Spec 001. Its iOS and phone-start cases remain separate.
